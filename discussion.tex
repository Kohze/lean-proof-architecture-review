\section{Discussion: preservation and reuse}
\label{sec:discussion}

\subsection{What the comparison reveals}

Across the six cases, the downstream operation determines the strength of
the required correspondence. An accuracy probability depends on the
output law. A named-coordinate equation depends on the coordinate map.
Ambient differentiation uses local information about a field. An
optimized inequality depends on the normalization and weights of its
estimates. The four recurring requirements---preservation of exact data,
laws, estimates, and local differential information---can occur together
within one development.

The most revealing comparisons concern a change in what the proof needs.
The common-base construction preserves a distribution through
reindexing, then preserves execution for a fixed input bank. Mahler first
identifies whole form-valued fields so that it can differentiate them,
then uses agreement on tangent tuples to compare boundary integrals.
The trace-cone construction recovers ideal order from addition alone,
then uses convergence and scalar compatibility to recognize the ideals
of a particular trace. In each case, following the next operation
explains why the interface has the fields it does.

Two cases also show how a small calculation can govern a large estimate.
For graph switches, the total-two matrix table identifies an exceptional
direction whose aggregate contribution is paid for by a projection
budget. For Crouzeix, rectangular compressions and two polynomial orders
produce energy bounds that close at the constant two. The important
relation is between the local calculation and the global quantity it
controls.

These patterns have substantial antecedents. Verified compilers establish
semantic preservation between source and implementation
\citep{Leroy2009,CakeML2014}; probabilistic program logics reason about
distributions and observations \citep{CertiCrypt2009,EasyCrypt2011}.
Algebraic hierarchy design and specification-driven collaboration treat
interfaces as mathematical objects
\citep{GarillotEtAl2009,Baanen2022,CommelinTopaz2024}. The contribution of
this comparison lies in showing the specific mathematical payload of
those interfaces and how their composition supports the selected proofs.

\subsection{Using the comparison in a new formalization}

Start with the intended downstream statement. Write the equation,
inequality, or event probability that the next step requires. Then identify
what the proposed representation changes: multiplicities, coordinate
order, multiplication order, or a neighborhood of definition. The
preservation statement should connect those changed data to the quantity
the next theorem consumes.

The examples in Section~\ref{sec:worked} make this choice concrete. For an
accuracy event, preserving a mean is insufficient; its indicator
expectation is enough, and a full output-law identity makes the interface
reusable for other events. For ambient differentiation, neighborhood
agreement is sufficient, while the later boundary integral may require
only agreement on tangent tuples. A named seam equation needs its
coordinate map. Proposition~\ref{prop:success-budget} then shows how
several such obligations can meet: sampling loss, tape uniformity, and
deterministic execution give one finite success count.

Finally, follow the construction of the hypotheses for the actual inputs.
The Mahler strip maps supply the analytic data, while the Crouzeix outer
domains supply strict containment and the required estimates. In the
marked-surface construction, using one splitting witness for the diagram
and its values keeps their identifications coherent. These examples
suggest reusable interfaces for a library: a small local model with a
measure-preserving correspondence, a sufficient semantic relation, and
explicit construction of the inputs that relation requires.

\subsection{Scope and further work}

Selection favored explicit interfaces that could be traced in depth.
It supports the present comparisons but does not estimate their frequency
or development cost across the collection. The source analysis establishes
what the inspected declarations state and how their constructions connect.
A full assessment of the headline mathematical results additionally
requires rebuilding their dependencies and examining the underlying
arguments, with the endpoint and support-result distinctions retained.

For a mathematician, these cases offer a route into substantial formal
source: locate the next operation, identify what it consumes, and follow
the theorem that preserves that information. For a formalizer, they point
to interfaces worth extracting into smaller libraries. The worked
examples provide a modest version of that extraction, exposing a
mathematical dependency in a form that can be inspected, reused, and tested.

\section*{Data and code availability}

The accompanying source package contains the LaTeX manuscript, verified
reference records, declaration evidence ledgers, original Lean examples,
and Python checks. The Lean examples use Lean 4.34.1 and import only
\src{Lean}; their compiler log records the axioms reported for the five
named theorems. The Python checks enumerate tape fibers and Boolean matrix
counts using exact integers. The package README gives reproduction
commands and identifies the pinned external sources. Public source links
in the manuscript resolve to the reviewed repository revision.

The source inventory is the complete Git tree of \src{openai/math},
inspected on 8 October 2026.\footnote{Reviewed revision:
\src{fd4aeeb2ee4fc729c18d98444fed42fd0529eeeb}. Public source links refer
to that revision.} It contains 122,875 files with the \src{.lean}
extension, including supporting modules. The separate formalization
catalogue lists 173 source records and 200 main-result bindings
\citep{OAICatalog}. These counts describe different units; none is a count
of the developments studied in depth here.


Proof checking supplies complementary evidence. The collection provides
Comparator challenge configurations \citep{OAIComparator}; the separately
inspected checker implements statement comparison, dependency and axiom
inspection, kernel replay, and an optional external checker
\citep{ComparatorSource2026}.\footnote{Checker source revision:
\src{ca04cfc72b550331658ec314bf47685281bfd4bf}. This pin records our
infrastructure reading; the collection's installation instructions do
not specify that revision.}
The distinction between constructing a proof and checking it has a long
history \citep{deBruijn1970,BarendregtWiedijk2005}; Lean typechecker
verification provides a contemporary example \citep{Carneiro2025Lean4Lean}.
Library maintenance addresses consistency at another level
\citep{vanDoornEbnerLewis2020}. Understanding why a formal statement
captures the intended mathematics still requires reading its objects
and hypotheses.
